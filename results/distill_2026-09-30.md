# LoRA distillation of the layout labels, CPU, 2026-09-30

Real numbers from two local runs of `slm_regime_classifier/distill_layout.py`. No API was
called. The teacher is the deterministic rule `ingestion/layout_labels.derive_label`, not a
frontier model; the frontier-as-teacher flow is designed in ADR-0012, not run.

## Setup

- Student: `HuggingFaceTB/SmolLM2-135M-Instruct`, LoRA r=16, alpha=32, dropout 0.05 on
  q/k/v/o projections: 1,843,200 trainable of 136,358,208 parameters. fp32, CPU.
- Task: the one-line feature string (`layout_labels.feature_string`) in, one label out.
- Data: 215 locally cached silver pages (10 arXiv PDFs, parsed offline) plus 400 synthetic
  pages (seed 2027), shuffled with seed 0. First 60 held out, next 300 used for training.
  Training labels: text 178, mixed 64, figure-heavy 26, table-heavy 24, scanned 8.
  Held-out labels: text 34, mixed 19, figure-heavy 3, scanned 2, table-heavy 2
  (19 silver, 41 synthetic). Always answering `text` scores 0.57 on the held-out set.
- Bounds: 300 examples max, 300 steps max, hard 25-minute training cap.
- Eval: greedy decoding, 6 new tokens, first label found in the reply; anything else is wrong.
- Machine: Intel Core i3-1000NG4 (2 physical cores, 4 logical), 8 GB RAM, macOS 15.7.
  A VM was also running and the machine was swapping (4.8 GB of swap in use).

## Why a separate Python 3.12 venv

`pip install torch` in the project venv (Python 3.13.11, macOS x86_64) fails with
`No matching distribution found for torch`. PyTorch's last Intel-macOS wheels are 2.2.2, built
for Python 3.12 and older. So the runs used a scratch Python 3.12.4 venv with torch 2.2.2,
numpy < 2, transformers 4.46.3 and peft 0.13.2. The latest transformers refuses torch 2.2
(`PyTorch >= 2.5 is required`), and the latest peft then fails to import. The `slm` extra in
`pyproject.toml` stays unpinned (`torch>=2.2`, `transformers>=4.46`, `peft>=0.13`,
`datasets>=2.20`); on Linux or Apple Silicon a normal `pip install -e '.[slm]'` works.

## Result

|---|---|---:|---:|---|---:|---:|---|---:|---:|
| 1 | shuffled, batch 8 | 40 of 300 (cap hit) | 1,510 s | 3.53 → 0.55 | 0.00 (60 invalid) | 0.57 (34/60) | text 59, table-heavy 1 | 2,258 ms | 1,190 ms |
| 2 | class-balanced, batch 4 | 127 of 300 (cap hit) | 1,507 s | 3.77 → 0.12 | 0.00 (60 invalid) | **0.87 (52/60)** | text 33, mixed 12, figure-heavy 9, scanned 3, table-heavy 3 | 1,621 ms | 1,319 ms |

Commands: run 1 `python slm_regime_classifier/distill_layout.py`; run 2
`python slm_regime_classifier/distill_layout.py --balanced --batch 4`. The saved adapter
(7.1 MB, git-ignored) and `slm_regime_classifier/adapter_card.md` are from run 2.

For comparison, the `rules` backend scores 0.92 on the same 60 held-out examples.

## What it supports

- The base model cannot do the task as prompted: all 60 replies contain no valid label.
- LoRA on a laptop CPU teaches the output format in 40 steps, and most of the rule in 127
  steps with class-balanced batches: 0.87 against a 0.57 majority baseline.
- Run 1 is the useful failure: with the natural label mix it collapsed to `text`, and its
  0.57 equals the majority baseline exactly. Accuracy alone would have hidden that; the
  prediction counts show it.

## What it does not support

- That the student is useful here. The rule it copies scores higher (0.92), costs $0 and runs
  in microseconds; the student needs about 1.3 s per page on this CPU. The kata proves the
  pipeline shape, not a win over code.
- Anything about the regime classifier, GPU QLoRA (4-bit needs CUDA; `--qlora` refuses to run
  without it), vLLM serving or pixel-level layout models. None of those were run.
- Training to convergence: both runs hit the 25-minute cap well short of 300 steps. The
  numbers are for a machine this slow, under load.
